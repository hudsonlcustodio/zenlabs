# Story P15.18 — Control provider health, balance and audit screens

- **Story ID**: `P15.18`

## User story

COMO administrator, QUERO to see provider health and credit balance and to read the audit trail, PARA a degrading provider and a governance question are both answerable from the product.

## Context

This is the provider health screen that `epic-P4` places out of its own scope and the audit viewing UI that `P5.09` defers. FR-C06 and FR-C07 fix the two views; `api-contracts.md` §5 fixes `GET /control/provider-health`, `GET /control/provider-balance` as `ADMIN` and `GET /control/audit` as `SUPER_ADMIN`.

## Acceptance criteria

- **AC-1** Provider health renders call rate, latency, error class, retry count, breaker state and rate-limit hits, the provider metrics named in `observability.md` §3.
- **AC-2** Balance renders Web/Studio credits and API credits as distinct kinds and never as a sum, because `provider-cost-ledger.md` §5 says they are not comparable under GATE-HG03.
- **AC-3** The audit view is `SUPER_ADMIN`-only and filters by `subjectType` and `actorId` exactly as `api-contracts.md` §5 declares; it is read-only, since the table is append-only under FF-11.
- **AC-4** Audit records display actor, role, subject, before and after, correlation id and IP, the fields `security-architecture.md` §9 requires, with no application-log content mixed in (`observability.md` §7).

## BDD examples

- EX-P15-01 GIVEN a `QA_REVIEWER` session, WHEN a Control screen route is requested, THEN the server denies it rather than rendering a filtered view.

## Verification gate

Class 6 coverage asserting audit is denied to every role below `SUPER_ADMIN`; integration coverage asserting the screen exposes no mutation path into `audit_record`.
