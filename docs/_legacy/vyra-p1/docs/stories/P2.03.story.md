# Story P2.03 — tenant and membership tables

## User story

COMO platform operator, QUERO the tenant root and its membership edge modelled first, PARA every client-owned row can reference a tenant that already exists.

## Context

`domain-model.md` §1 and `database-schema.md` §3.1. Module `tenancy` owns the invariant that no client-owned row exists without `tenant_id`.

## Acceptance criteria

- **AC-1** `tenant` exists with lifecycle status and the columns fixed by `database-schema.md` §3.1.
- **AC-2** `membership` links a user to a tenant with a role, and is itself tenant-scoped.
- **AC-3** The MVP limit of one portal user per tenant is enforced as policy, not as a schema constraint (brief §7).

## BDD examples

- EX-P2-03a GIVEN the schema, WHEN a second portal membership is created for a tenant, THEN the policy layer rejects it while the schema remains capable of representing it.
