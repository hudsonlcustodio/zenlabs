# Story P16.02 — Alarms for every condition in `observability.md` §4

- **Story ID**: `P16.02`
- **Epic**: `P16` (`docs/epics/epic-P16.md`)

## User story

COMO platform operator, QUERO every alarm in the contract to exist with its stated condition and severity, PARA a critical failure pages someone instead of waiting for a client to notice.

## Context

`observability.md` §4 tabulates seventeen alarms with conditions and severities, and states that the sustained windows there define the `scalability-gates.md` §1 thresholds. `P7.02` and `P7.07` explicitly named this story as the consumer of relay lag, loop lag and stuck-item counts.

## Acceptance criteria

- **AC-1** Every row in `observability.md` §4 exists as an alarm with its stated condition, window and severity; an inventory test compares the defined set against the table.
- **AC-2** Relay lag, reconciliation loop lag and stuck-item counts have alarms, closing the forward references from `P7.02` AC-4 and `P7.07` AC-4.
- **AC-3** Thresholds and windows are configuration, not literals, consistent with the `observability.md` §4 note that windows define the `scalability-gates.md` §1 thresholds.
- **AC-4** Critical-severity alarms — provider auth error, consent revocation propagation failure, secret scan finding — are distinguishable from high severity in routing, not only in a label.

## BDD examples

- EX-P16-02 GIVEN any alarm listed in `observability.md` §4, WHEN the runbook index is checked, THEN a runbook entry exists for it and names an owner action.

## Verification gate

Alarm-inventory test green: the defined alarm set equals the `observability.md` §4 table, with no extra and no missing row.
