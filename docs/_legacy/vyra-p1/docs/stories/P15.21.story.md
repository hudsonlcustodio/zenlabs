## User story

COMO product owner, QUERO responsiveness and accessibility verified as requirements rather than promised as polish, PARA NFR-14 is a property of the build instead of an intention.

## Context

NFR-14 states that responsiveness and accessibility are architectural requirements, not later polish, and ADR-0003 repeats it as a consequence of the stack choice. ADR-0028 removes the Storybook catalogue, so verification is targeted component tests plus the running application — the only sanctioned substitute.

**Scope.** This story asserts conformance for the routes **this epic renders**, using the harness `P18.16` already built. The product-wide conformance suite across all three surfaces — the per-surface responsive commitment matrix, the keyboard journeys, the composed-screen contrast pass, the motion budget, the performance budgets and the 14-criterion blueprint audit — is epic `P24`, at wave 12. The two are deliberately different in scope and neither substitutes for the other.

## Acceptance criteria

- **AC-1** Every critical screen is asserted operable at the declared breakpoint set, with the set held as configuration rather than as literals scattered through components.
- **AC-2** Keyboard operability and accessible naming are asserted for every route this epic renders, reusing the `P18.16` harness rather than building a second one.
- **AC-3** Verification uses component tests plus the running application, and adds no Storybook page-story, per ADR-0028.
- **AC-5** The breakpoint set asserted here matches the per-surface commitment matrix of `VYRA_PRODUCT_EXPERIENCE.md` §22.1, so this story and `P24.01` cannot disagree about what each surface promises.
- **AC-4** NFR-03 critical screen load is treated as measurable here and actually measured in `P16.09`; this story does not assert a latency number it cannot produce without staging.

## BDD examples

- EX-P15-07 GIVEN the smallest supported breakpoint, WHEN a critical screen renders, THEN it stays operable and the accessibility assertions pass.
