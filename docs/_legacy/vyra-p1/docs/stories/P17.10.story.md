# Story P17.10 — CI stage 8: migration validation with destructive-change detection

- **Story ID**: `P17.10`
- **Epic**: `P17` (`docs/epics/epic-P17.md`)

## User story

COMO implementing agent, QUERO que toda migração seja aplicada contra um snapshot restaurado de staging antes de tocar qualquer ambiente, PARA que uma mudança destrutiva seja recusada pelo pipeline e não descoberta em produção.

## Context

`cicd.md` §1 stage 8 requires a forward migration on a **restored staging snapshot** plus destructive-change detection, and §4 states that destructive changes are never applied automatically: a migration containing `DROP`, a destructive `ALTER ... TYPE`, or `NOT NULL` without a default must follow the expand/contract procedure in `migrations.md` §3. `P2.02` builds the detector as a tool; this story makes it a blocking pipeline stage against real, restored data.

## Acceptance criteria

- **AC-1** Stage 8 restores the most recent staging snapshot into an ephemeral instance and applies every pending migration forward, failing on any error. No environment's live database is touched.
- **AC-2** The destructive-change detector from `P2.02` runs against the pending set and fails the stage when an unguarded `DROP`, destructive `ALTER ... TYPE`, or `NOT NULL` without a default is present, naming the migration and the statement.
- **AC-3** A migration explicitly following the expand/contract procedure of `migrations.md` §3 passes, so the rule blocks unsafe changes without blocking safe evolution. The passing path is asserted with a fixture, not only the failing one.
- **AC-4** The stage records the applied migration list and the elapsed time, and fails if a migration exceeds a configured duration budget — because a migration that locks for minutes is a production incident regardless of its correctness.
- **AC-5** Production migrations run as a distinct, gated step with a recorded operator identity (`cicd.md` §4); the pipeline refuses to apply to production without that record.
- **AC-6** The ephemeral instance is destroyed at the end of the stage, in success and in failure, and its destruction is asserted.

## BDD examples

- EX-P17-05 GIVEN a migration containing an unguarded `DROP`, WHEN stage 8 runs, THEN it fails and no environment is touched.
- EX-P17-25 GIVEN a migration following the expand/contract procedure, WHEN stage 8 runs, THEN it passes.
- EX-P17-26 GIVEN a production apply without a recorded operator, WHEN the gated step is evaluated, THEN it is refused.

## Verification gate

Stage 8 is blocking on the default branch; the restore-and-apply path succeeds against a real snapshot; the seeded unguarded destructive migration fails naming the statement; the expand/contract fixture passes; the ephemeral instance is destroyed in both outcomes; a production apply without an operator record is refused.
