## User story

COMO administrador, QUERO suspender ou reativar um tenant sabendo exatamente o que isso interrompe, PARA que uma decisão comercial nunca tenha uma consequência técnica invisível.

## Context

`FR-C01` covers tenant management. Suspension is not a flag: `T22` moves affected items to `BLOCKED` when a subscription is suspended, which stops content requests and approvals for that tenant. `VYRA_PRODUCT_EXPERIENCE.md` §33.2 requires the downstream effect to be stated at the moment of the decision.

## Acceptance criteria

- **AC-1** The tenant grid renders over `P19.03` with status, plan and a consumption mini-meter; tenant detail renders `L-object` with Overview, Plan, Users, Integrations and Audit tabs.
- **AC-2** Create, suspend and reactivate are destructive-guarded per `P18.09` AC-6 and gated by MFA re-assertion (`P23.01` AC-2).
- **AC-3** Suspension states its downstream effect **before** confirmation: content requests and approvals stop, and in-flight items move to `BLOCKED` via T22. The affected in-flight count is shown.
- **AC-4** A suspended tenant renders with a danger tint in the grid and remains openable; nothing about a suspended tenant is hidden from an administrator.
- **AC-5** Every tenancy action writes an audit record visible from the tenant's Audit tab and from the audit explorer (`P23.09`).

## BDD examples

- EX-P23-12 GIVEN a tenant with in-flight items, WHEN suspension is confirmed, THEN the affected count and the T22 consequence were stated beforehand.
- EX-P23-13 GIVEN a suspended tenant, WHEN the grid renders, THEN the row is danger-tinted and still openable.

## Verification gate

Grid and detail render with all tabs; create, suspend and reactivate are destructive-guarded and MFA-gated; suspension states the T22 consequence and the affected in-flight count before confirmation; suspended tenants render distinctly and remain accessible; every action produces a visible audit record.
