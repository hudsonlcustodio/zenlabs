## User story

COMO tenant, QUERO metrics collected on a schedule after publication, PARA I get an early signal and a long-tail view without anyone pressing refresh.

## Context

FR-PF04 requires asynchronous collection in windows after publication. `performance.md` §3 fixes the four windows — +1 h, +24 h, +7 d, +30 d — with `captured_bucket` as the window label, and states that windows are configuration, not constants. `workflows-state-machines.md` §7 lists the metric collector as a windowed reconciliation loop, and T19 schedules the windows on publication success.

## Acceptance criteria

- **AC-1** On T19 the four collection windows are scheduled relative to publication time, each labelled by its `captured_bucket` (`performance.md` §3).
- **AC-2** The window set is configuration and can be changed without a code change; `performance.md` §3 states windows are configuration, not constants.
- **AC-3** Collection runs asynchronously on the P7 worker harness with tenant context, never on a request path (FR-PF04).
- **AC-4** The metric collector appears as a windowed loop alongside the other reconciliation loops (`workflows-state-machines.md` §7) and exposes loop lag on the same convention as `P7.07`.

## BDD examples

- EX-P14-02a GIVEN a publication completed at T, WHEN the windows are scheduled, THEN collections are due at T+1 h, T+24 h, T+7 d and T+30 d with their bucket labels.

## Verification gate

Integration test asserting the four windows are scheduled from a completed publication and that changing the configured window set changes the schedule without a code change.
