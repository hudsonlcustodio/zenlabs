# Story P16.08 — Operational dashboards

- **Story ID**: `P16.08`

## User story

COMO platform operator, QUERO the six dashboards in the observability contract to exist, PARA the monthly gate review in `scalability-gates.md` §4 has the metric series it requires.

## Context

`observability.md` §5 names six dashboards: pipeline health, provider health, commercial, platform, security and governance. `scalability-gates.md` §4 reviews gates monthly against CloudWatch dashboards and requires the triggering metric series before any promotion.

## Acceptance criteria

- **AC-1** All six dashboards from `observability.md` §5 exist with the content each one names.
- **AC-2** Dashboards read the metric names defined in `P16.01`; none defines its own query against a name no emitter produces.
- **AC-3** The commercial dashboard distinguishes client usage from VYRA provider cost, which FR-PC01 keeps as separate ledgers, and labels `estimated` cost entries as estimated under GATE-COST01.
- **AC-4** No target line is drawn for a success metric, because `prd.md` §11 records that thresholds require a commercial decision (OQ-03).
- **AC-5** The platform dashboard records the **availability SLO** explicitly: `NFR-04` (≥ 99.5% initial) is stated as the target with its measurement window and its breach action, so the number lives somewhere a person can act on rather than only in the PRD. `NFR-05` (≥ 99.9% at maturity) is recorded on the same panel as a **maturity target explicitly out of MVP scope**, and no alarm is defined against it — because an SLO nobody has committed to is an alarm nobody will answer. This closes debt D-05.

## BDD examples

- EX-P16-02 GIVEN any alarm listed in `observability.md` §4, WHEN the runbook index is checked, THEN a runbook entry exists for it and names an owner action.

## Verification gate

Dashboard-inventory test asserting six dashboards exist and that every widget references a metric name emitted by `P16.01`.
