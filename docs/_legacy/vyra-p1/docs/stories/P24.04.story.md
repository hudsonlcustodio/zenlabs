## User story

COMO implementing agent, QUERO contraste verificado em telas reais nos dois temas, PARA que a prova em nível de token não seja invalidada pela composição.

## Context

`P18.02` AC-4 proves contrast for every semantic token pair headlessly. That proof is necessary and insufficient: a screen can place a `text-tertiary` label on a `surface-3` hover state, or a chart series on a tinted card, producing a pair the token test never evaluated. §34 C-11 makes contrast a screen criterion.

## Acceptance criteria

- **AC-1** Every screen is rendered in **both** themes and every actual foreground/background pair present in the render is evaluated against the §5.5 minimums — including hover, selected, disabled and tinted-surface states.
- **AC-2** Chart series are evaluated against their real plot background on the real screen, and adjacent series are checked for the §5.5 distinguishability requirement.
- **AC-3** Focus rings are evaluated against **both** their inner and outer neighbours on each screen, since a ring that passes on `bg-base` can fail on `surface-3`.
- **AC-4** `prefers-contrast: more` is evaluated as a third pass with the raised token set from `P18.02` AC-5.
- **AC-5** A failure names the screen, the theme, the element pair and the measured ratio, so the fix is unambiguous.

## BDD examples

- EX-P24-03 GIVEN any screen in either theme, WHEN the composed-contrast check runs, THEN every foreground/background pair meets its §5.5 minimum.
- EX-P24-12 GIVEN a focus ring on a `surface-3` row, WHEN contrast is measured against both neighbours, THEN both meet 3:1.

## Verification gate

Both themes and the raised-contrast pass are green for every screen across rest, hover, selected, disabled and tinted states; chart series pass against their real plot background with adjacent distinguishability; focus rings pass against both neighbours; a seeded failing pair reports screen, theme, pair and ratio.
