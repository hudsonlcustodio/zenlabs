# Story P16.05 — Provider balance sync loop and low-balance handling

- **Story ID**: `P16.05`
- **Epic**: `P16` (`docs/epics/epic-P16.md`)

## User story

COMO platform operator, QUERO provider credit balance polled on a schedule and acted on when it runs low, PARA a depleted provider account degrades gracefully instead of failing renders repeatedly.

## Context

`epic-P4` records OQ-P4-01: whether balance polling belongs to the breaker or to the operations epic, with the port shape fixed in P4 and the resolution deferred here. `provider-cost-ledger.md` §5 fixes hourly sync into `provider_balance`, distinct balance kinds under GATE-HG03, configuration thresholds, and `BLOCKED` via T22 rather than repeated failure. `workflows-state-machines.md` §7 lists the loop at hourly cadence.

## Acceptance criteria

- **AC-1** OQ-P4-01 is resolved here: balance polling is an operations loop, not breaker behaviour. The breaker keeps reacting to call outcomes; the loop reads balance on the hourly cadence in `workflows-state-machines.md` §7.
- **AC-2** Web/Studio credits and API credits are stored as distinct balance kinds and never summed, per `provider-cost-ledger.md` §5 and GATE-HG03.
- **AC-3** A balance below its configured per-provider threshold fires the "Provider low balance" alarm from `observability.md` §4 and notifies through `P16.06`, which FR-NT01 lists as a trigger.
- **AC-4** A depleted balance moves affected items to `BLOCKED` through T22 rather than letting them fail repeatedly, exactly as `provider-cost-ledger.md` §5 states.

## BDD examples

- EX-P16-04 GIVEN a provider credit balance below its configured threshold, WHEN the hourly sync runs, THEN the low-balance alarm fires and affected items move to `BLOCKED` via T22 rather than failing repeatedly.
