# Story P16.01 — Metric emission across every observability domain

## User story

COMO platform operator, QUERO every metric domain in the observability contract actually emitted, PARA the alarms and dashboards that follow have real series instead of gaps.

## Context

`observability.md` §3 tabulates thirteen metric domains: API, queues, generation, ingestion, QA, providers, usage, cost, publication, knowledge, identity and auth. Earlier stories declared they would expose specific signals and deferred the emission here: routing decisions from `P10.03` AC-5, relay lag from `P7.02` AC-4, loop lag and stuck-item counts from `P7.07` AC-4, and queue age from `P7.03` AC-4.

## Acceptance criteria

- **AC-1** Every domain in `observability.md` §3 emits its listed metrics through `packages/observability` metric emitters, which `architecture.md` §2.2 names as that package's contents.
- **AC-2** The deferred signals are present and named: model routing decisions (`P10.03`), outbox relay lag (`P7.02`), reconciliation loop lag and stuck-item counts (`P7.07`), queue oldest-message age (`P7.03`).
- **AC-3** Ingestion metrics include the committed-without-asset count that `observability.md` §3 lists, because that is the RISK-19 signal.
- **AC-4** Metric dimensions carry `tenantId` only as the opaque UUID `observability.md` §1 permits, and never a personal attribute.
- **AC-5** A metric name is defined once and consumed by alarms and dashboards, so `P16.02` and `P16.08` cannot drift from the emitter.

## BDD examples

- EX-P16-09 GIVEN a correlation identifier accepted at the edge, WHEN the work traverses HTTP, outbox, queue and worker, THEN every emitted record carries the same identifier.

## Verification gate

Integration coverage asserting each domain in `observability.md` §3 produces at least one metric under exercise, and that the four deferred signals are among them.
