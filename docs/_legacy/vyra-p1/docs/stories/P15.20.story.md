# Story P15.20 — Screen-level rendering rules driven by the route manifest

## User story

COMO architect, QUERO what a screen renders to be derived from the same manifest that declares route guards, PARA a hidden control and a denied route can never disagree.

## Context

`P3.07` builds a machine-readable manifest generated from the routes themselves and explicitly reserves screen-level rendering rules for this story. `api-contracts.md` §2 states that UI hiding is never an authorization mechanism, so the rendering rule is a presentation consequence of the guard, never a second source of truth.

## Acceptance criteria

- **AC-1** Rendering rules read the P3.07 manifest; no screen maintains its own copy of a role or capability list.
- **AC-2** Hiding a control is presentation only; the guarded route still denies the call, and `P15.22` proves it.
- **AC-3** A manifest entry with no corresponding rendering rule is reported, so a new guarded route cannot be silently unrepresented on its surface.
- **AC-4** The rules are consumed by the class 6 suite, which `P3.07` already makes the manifest available to.

## BDD examples

- EX-P15-02 GIVEN a screen that hides an action for a role, WHEN the underlying route is called directly, THEN the server denies it.
- EX-P15-06 GIVEN a rendered route added without a guard declaration, WHEN CI runs, THEN FF-17 fails naming the route.

## Verification gate

Class 6 suite consuming the manifest-derived rules; integration test asserting a hidden control's route still denies a direct call.
