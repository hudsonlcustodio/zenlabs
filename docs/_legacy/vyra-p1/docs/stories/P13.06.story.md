## User story

COMO tenant, QUERO my schedule honoured even if the process restarts, PARA the calendar is a commitment rather than an intention held in memory.

## Context

ADR-0010 fixes `scheduled_publication.scheduled_for` as the source of truth with a dispatcher that runs each minute and claims due rows using `FOR UPDATE SKIP LOCKED`. SQS delivery delay is capped at 15 minutes and therefore cannot express an editorial calendar. FR-CA02 requires scheduling to be reliable and recoverable after process restart.

## Acceptance criteria

- **AC-1** A dispatcher loop selects due rows with `FOR UPDATE SKIP LOCKED` and enqueues publish jobs onto the P7 queues; the cadence is configuration, with one minute as the documented value (`workflows-state-machines.md` §6, §7).
- **AC-2** T18 (`SCHEDULED → PUBLISHING`) executes only when the schedule is due and the token is valid, and compensates back to `SCHEDULED` on a non-terminal failure.
- **AC-3** Pre-flight at dispatch re-checks token validity, connection health, quota availability, disclosure resolvability and active consent (`social-publishing.md` §4).
- **AC-4** Restart safety is structural: no schedule state lives in process memory, so a restart resumes from the table (ADR-0010).
- **AC-5** Concurrent dispatchers never claim the same row, and publication counts by status and error class feed the `Publication` metrics in `observability.md` §3.

## BDD examples

- EX-P13-04 GIVEN due schedules and a dispatcher restart, WHEN the dispatcher resumes, THEN the due rows are still claimed exactly once from the table.

## Verification gate

Integration test with two concurrent dispatchers over the same due set asserting single claim, a restart test asserting resumption, and class 9 coverage of the publish job's retry and DLQ routing.
