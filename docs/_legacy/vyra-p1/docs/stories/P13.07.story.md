## User story

COMO tenant, QUERO my approved video published to Instagram and Facebook through the official API, PARA reach is legitimate and my accounts are never put at risk.

## Context

`provider-architecture.md` §1 declares `MetaPublishingProvider` behind the `PublishingProvider` port with `publish`, `fetchMetrics` and `refreshToken`. `prd.md` §9.4 and `social-publishing.md` §2 record the confirmed Meta constraints: Business or Creator account linked to a Page, admin-equivalent permission, possible PPA, possible 2FA, and 100 API-published posts per rolling 24 hours.

## Acceptance criteria

- **AC-1** `MetaPublishingProvider` implements the port and lives in `packages/providers`; no domain or application code imports the SDK (FF-02, FF-03).
- **AC-2** Each documented Meta failure — PPA missing, 2FA missing, insufficient Page role, invalid token, rate limit — maps to a declared error class in the P4 taxonomy, with `connection_invalid` and `rate_limited` among the stable codes (`api-contracts.md` §1.1).
- **AC-3** A rate-limit response reschedules with backoff inside the publication window rather than failing the item (`social-publishing.md` §5).
- **AC-4** Success returns an `ExternalPostRef` carrying the platform post id; nothing else in the flow invents one.
- **AC-5** Scope names and quotas resolve from configuration; GATE-MT02 is unresolved, so the affected fixture is marked provisional and its adapter test is skipped with an explicit gate reference rather than asserting a guessed shape (`testing-strategy.md` §3).

## BDD examples

- EX-P13-07a GIVEN a Meta rate-limit response, WHEN publication is attempted, THEN it is rescheduled with backoff inside the window and the item is not failed.

## Verification gate

Class 4 adapter tests mapping every recorded failure fixture to its error class, run under `PROVIDER_MODE=mock` with no billable call (FF-08).
