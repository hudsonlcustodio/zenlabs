## User story

COMO security reviewer, QUERO the database itself to refuse cross-tenant access, PARA an application bug cannot become a data breach.

## Context

`architecture.md` §5 mandates four layers of defence with RLS as the authoritative one, keyed on `current_setting('vyra.tenant_id')`.

## Acceptance criteria

- **AC-1** Every client-owned table has an RLS policy keyed on the tenant GUC and RLS is enabled and forced.
- **AC-2** `vyra_app` is not the table owner and does not hold `BYPASSRLS`.
- **AC-3** A query issued without the GUC set returns zero rows rather than all rows.
- **AC-4** Tables listed in `database-schema.md` §2.1 as legitimately nullable-`tenant_id` are enumerated explicitly and each is justified in the schema.
- **AC-5** Policies cover SELECT, INSERT, UPDATE and DELETE, not SELECT alone.

## BDD examples

- EX-P2-01 GIVEN two seeded tenants, WHEN tenant A queries any client-owned table without its GUC, THEN zero rows are returned rather than tenant B's rows.
