# Story P21.09 — Approval experience: script and video decision surfaces

## User story

COMO cliente, QUERO aprovar sabendo exatamente o que a aprovação inicia e quanto consome, PARA que a única ação obrigatória do produto seja também a mais clara.

## Context

Approval is the only mandatory client action and the moment usage becomes billable: T08 reserves and T11 commits, and `ADR-0018` makes the commit final. `VYRA_PRODUCT_EXPERIENCE.md` §28 fixes the surface in eight parts, including the consequence statement, the guard-driven disabled states and idempotency. `EX-P15-03` requires a rejection without a reason to be refused by the API and rendered as `validation_failed`.

## Acceptance criteria

- **AC-1** Script approval renders the `L-workspace` of §28.2: context rail (objective, channel, format, target duration, brand rules), read-only script canvas at `body-lg` and 68ch, inspector (version history, runtime estimate, compare with the previous version), and a pinned decision bar carrying **exactly two** controls — `Approve` and `Request revision`.
- **AC-2** Video approval renders the same skeleton with the `P19.05` player as canvas, the approved script in the context rail, QA notes in the inspector, and side-by-side comparison against revision *n-1* where one exists (§24.5, §28.3).
- **AC-3** **The consequence is stated, not hidden**: a one-line statement above `Approve` names what approval starts and the number of minutes it reserves. It is not a tooltip and not a per-approval modal (§28.4, PD-07).
- **AC-4** Guard-driven disabling: when the reservation would exceed entitlement, `Approve` is disabled with the `entitlement_exhausted` reason and a link to the plan; when consent is not active, it is disabled with the `consent_revoked` reason and a link to consent (G-1, G-2, `FF-30`). The screen never lets the user attempt an action the guard will refuse.
- **AC-5** `Request revision` requires a reason, states its minimum length, offers optional structured tags (tone, accuracy, length, compliance) and shows the revision budget. At the last permitted revision it states that the next rejection moves the item to `BLOCKED` — **before** it happens (T07, §25.4).
- **AC-6** Idempotency: approval sends an `Idempotency-Key` derived from the object and version; the control disables on first click and re-enables only on a terminal response; a duplicate submission resolves to the same outcome and renders the resulting state, never an error (§28.5).
- **AC-7** A concurrent change resolves honestly: `state_transition_not_allowed` refreshes the screen to the true state and explains that someone else acted, rather than retrying blindly.
- **AC-8** Auto-approved items (policy `AUTO`, T05/T15) render read-only, name the policy that approved them and show the brand-compliance result that permitted it (G-4); the QA row states that VYRA QA was performed and cannot be skipped by a tenant setting (`FF-33`, `ADR-0033`).

## BDD examples

- EX-P15-03 GIVEN a rejection submitted without a reason, WHEN the approval screen posts it, THEN the API refuses it and the screen renders the stable `validation_failed` code.
- EX-P21-02 GIVEN a 320px viewport and keyboard-only input, WHEN a client approves a script, THEN the approval completes end-to-end.
- EX-P21-04 GIVEN consent is not active, WHEN the approval screen renders, THEN Approve is disabled with the consent reason and a link to consent.
- EX-P21-07 GIVEN a double-submitted approval, WHEN the second request arrives, THEN it resolves to the same outcome and renders the resulting state, not an error.

## Verification gate

Both approval surfaces render the `L-workspace` with a two-control decision bar; the consequence statement is present above Approve with the reserved minute count; entitlement and consent guards disable Approve with their reasons and links; rejection requires a reason and renders `validation_failed` when omitted; the last-revision warning appears before the final rejection; idempotent double submission resolves to one outcome; a concurrent change refreshes to the true state; auto-approved items render read-only with policy and compliance evidence; the whole flow completes at 320px by keyboard.
