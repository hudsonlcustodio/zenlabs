## User story

COMO platform operator, QUERO the latency targets measured against staging before launch, PARA NFR-01, NFR-02 and NFR-03 are results rather than aspirations.

## Context

`testing-strategy.md` class 14 places load tests in `tests/load/`, executed before production launch against staging and after any gate promotion, verifying NFR-01, NFR-02 and NFR-03. `implementation-sequencing.md` Phase 15 makes those three the acceptance gate. `P15.21` AC-4 defers the NFR-03 measurement here because it needs staging.

## Acceptance criteria

- **AC-1** The suite lives in `tests/load/` and runs before production launch and after any gate promotion, per `testing-strategy.md` class 14 and §6.
- **AC-2** It asserts API read P95 under 500 ms (NFR-01), API write P95 under 800 ms (NFR-02) and critical screen load under 3 s (NFR-03).
- **AC-3** It runs against staging, which `aws-topology.md` §7 keeps fully separated, and with `PROVIDER_MODE` non-live unless an explicit, time-boxed live test is authorised — so no run spends provider credit by accident (FF-08, NFR-13).
- **AC-4** The load profile — concurrent tenants, request mix and duration — is recorded alongside the results, because no artifact fixes it and an unrecorded profile makes the result unreproducible (OQ-P16-03).

## BDD examples

- EX-P16-06 GIVEN staging under the declared load profile, WHEN the class 14 suite runs, THEN P95 read latency is under 500 ms, P95 write latency is under 800 ms and critical screen load is under 3 s.

## Verification gate

Class 14 suite executed against staging with NFR-01, NFR-02 and NFR-03 met and the load profile recorded with the run.
