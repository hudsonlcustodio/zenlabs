# Story P5.06 — Revocation with propagation tracking

## User story

COMO identity owner, QUERO revocation that stops generation immediately and is tracked to the provider, PARA revocation is a fact rather than an intention.

## Context

FR-ID04 requires revocation to prevent new generations; FR-ID05 requires propagation to external providers to be planned. Module 21's invariant: revocation propagates before it is reported done. T22 routes affected items to BLOCKED.

## Acceptance criteria

- **AC-1** Revocation takes effect on the local guard immediately, before any provider round-trip.
- **AC-2** Propagation to each bound provider is tracked with its own status and retry budget.
- **AC-3** Revocation status distinguishes locally-effective from fully-propagated and never reports done while propagation is pending.
- **AC-4** In-flight items are routed to BLOCKED via T22, releasing held reservations only and never reversing a commit.
- **AC-5** Revocation writes an audit record naming actor, time and the versions active.

## BDD examples

- EX-P5-01 GIVEN consent revoked between script approval and render, WHEN the render is attempted, THEN the item moves to BLOCKED and no provider submission occurs.
- EX-P5-04 GIVEN a revocation whose provider propagation has not been confirmed, WHEN revocation status is read, THEN it reports propagation pending rather than complete.

## Verification gate

Integration plus class 13 consent-enforcement tests including the revoke-between-approval-and-render case.
