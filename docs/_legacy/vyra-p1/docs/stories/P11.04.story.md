## User story

COMO platform operator, QUERO one attempt to produce at most one provider submission, PARA a retry can never double-charge the client or the business.

## Context

`provider-architecture.md` §6 fixes idempotent submission; T10 keys on `sha256(attemptId)`; module 11's invariant is one attempt to one provider submission. `testing-strategy.md` §2.4 names duplicate submission a highest-value test.

## Acceptance criteria

- **AC-1** Submission is keyed on `sha256(attemptId)` and enforced by the P7.05 idempotency table.
- **AC-2** Once a `providerJobId` is stored, any retry polls that job rather than submitting again.
- **AC-3** A crash between submission and persistence is recovered by reconciliation rather than by resubmission (`provider-architecture.md` §7).
- **AC-4** T10's retry policy of five jittered attempts applies to the submission call, not to the creation of new jobs.
- **AC-5** Every submission path declares its idempotency key, satisfying FF-28.

## BDD examples

- EX-P11-01 GIVEN an attempt with a stored `providerJobId`, WHEN a retry occurs, THEN it polls the existing job and submits nothing.
