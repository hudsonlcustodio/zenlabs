# Story P13.03 — Token refresh, revocation detection and connection health

## User story

COMO tenant, QUERO expiring tokens refreshed and revoked ones detected, PARA a silent authorization loss surfaces as a fixable warning instead of a failed publication.

## Context

`social-publishing.md` §2.2 specifies an hourly refresh job for tokens approaching expiry and notification of the tenant on failure; revocation at the platform is detected on the next call and moves the connection to `invalid`. `workflows-state-machines.md` §7 already lists `Token refresh | hourly | social_connection nearing expiry` as a reconciliation loop.

## Acceptance criteria

- **AC-1** An hourly loop refreshes connections nearing `token_expires_at`, using the `PublishingProvider.refreshToken(ConnectionRef)` port operation (`provider-architecture.md` §1); the refresh window is configuration.
- **AC-2** A failed refresh moves the connection to `expiring` or `invalid` per §2.2 and raises the `social integration expiring` notification event from FR-NT01; delivery is P16.
- **AC-3** A call rejected because the platform revoked authorization moves the connection to `invalid` and blocks further scheduling with a remediation message (`social-publishing.md` §5).
- **AC-4** A publication that fails on an invalid or expired token returns the item to `READY` rather than failing it terminally (`social-publishing.md` §5).

## BDD examples

- EX-P13-05 GIVEN a token revoked at the platform, WHEN the next call runs, THEN the connection moves to `invalid`, the item returns to `READY`, and scheduling is blocked with remediation text.

## Verification gate

Integration test over refresh, expiry and revocation transitions, plus class 9 coverage of the retry and error-class routing for the refresh job.
