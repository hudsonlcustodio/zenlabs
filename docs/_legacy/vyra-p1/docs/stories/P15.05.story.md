## User story

COMO portal user, QUERO to submit a content request by filling in what is genuinely required, PARA requesting content is not itself a chore.

## Context

This is the request UI that `P8.01` places out of its own scope. FR-P02 requires the submission surface; `api-contracts.md` §3.1 fixes the body, where only `objective` and `channel` are required and everything else is optional (FR-CR03).

## Acceptance criteria

- **AC-1** The form marks only `objective` and `channel` as required, matching `api-contracts.md` §3.1; adding a required field would contradict FR-CR03.
- **AC-2** Submission sends an `Idempotency-Key`, as `api-contracts.md` §1 requires for creating POSTs, so a double submit produces one request.
- **AC-3** Validation failures render the stable `validation_failed` code from `api-contracts.md` §1.1 rather than a hand-written message per field origin.
- **AC-4** The optional fields offered are exactly those in the §3.1 body — `subject`, `campaignId`, `references`, `guidance`, `format`, `priority`, `desiredDate` — with none invented.

## BDD examples

- EX-P15-03 GIVEN a rejection submitted without a reason, WHEN the approval screen posts it, THEN the API refuses it and the screen renders the stable `validation_failed` code.

## Verification gate

Class 3 contract test of the submission payload against the `packages/contracts` schema, plus an integration test asserting double submission yields one request.
