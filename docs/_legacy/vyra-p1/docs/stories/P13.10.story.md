# Story P13.10 — Publication result handling (T19, T20) and failure classes

## User story

COMO operations manager, QUERO every publication outcome recorded with its error class, PARA a failure is diagnosable and a success is never double-counted.

## Context

T19 stores `externalPostId` and schedules metric windows on success; T20 records the error class on terminal platform rejection with 3 retries then DLQ, and reverts to `READY` on operator action. `social-publishing.md` §5 enumerates the failure classes; §4 states that a retry finding an existing `external_post_id` returns success without re-posting.

## Acceptance criteria

- **AC-1** T19 writes `external_post_id` exactly once per publication (I-SP2) and emits `PublicationCompleted` through the P8 engine.
- **AC-2** A retry that finds an existing `external_post_id` returns success without a second platform call (`social-publishing.md` §4).
- **AC-3** T20 records `last_error_class` on terminal rejection, retries 3 times then routes to the DLQ, and supports operator-initiated revert to `READY`.
- **AC-4** Every failure class in `social-publishing.md` §5 has a distinct handling path: invalid token, platform rate limit, content rejected, PPA/2FA missing, unaudited restriction.
- **AC-5** T19 triggers scheduling of the metric collection windows consumed by `P14.02`; the windows themselves are defined there.

## BDD examples

- EX-P13-10a GIVEN a publication with a stored `external_post_id`, WHEN the job is retried, THEN success is returned and no platform call is made.
