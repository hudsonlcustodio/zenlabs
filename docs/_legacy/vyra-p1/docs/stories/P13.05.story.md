# Story P13.05 — Scheduling endpoint (T17) and schedule cancellation

- **Story ID**: `P13.05`

## User story

COMO publisher, QUERO to schedule a ready item to a connected channel at a future time, PARA publication is planned editorially instead of triggered by hand.

## Context

T17 moves `READY → SCHEDULED` for a `PUBLISHER`, requires a connected channel and a future `scheduledFor`, creates a `ScheduledPublication` and is keyed on `contentItemId+channelId`. P8.07 implemented the transition; this story exposes it and persists the row with its indexes.

## Acceptance criteria

- **AC-1** `POST /content-items/{id}/schedule` with `channelId*`, `scheduledFor*` and `mode` executes T17, restricted to the `PUBLISHER` role (`api-contracts.md` §3.3, §2).
- **AC-2** `scheduled_publication` carries `content_item_id`, `channel_id`, `scheduled_for`, `mode`, `status`, `external_post_id`, `attempt_count` and `last_error_class`, with `UNIQUE (content_item_id, channel_id) WHERE status <> 'cancelled'` and `INDEX (scheduled_for) WHERE status = 'scheduled'` (`database-schema.md` §3.6).
- **AC-3** Scheduling is refused when the connection is not healthy per `P13.04` or when `scheduledFor` is not in the future, using the stable codes `connection_invalid` and `validation_failed` (`api-contracts.md` §1.1).
- **AC-4** `DELETE /scheduled-publications/{id}` cancels the schedule and sets a status that frees the partial unique index for a later reschedule.

## BDD examples

- EX-P13-05a GIVEN an item already scheduled to a channel, WHEN it is scheduled to that channel again, THEN the unique partial index refuses the second row.
