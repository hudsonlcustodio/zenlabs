# Story P16.04 — Retention jobs for every dataset and FF-31

## User story

COMO governance owner, QUERO every retained dataset to have an enforced expiry, PARA retention is a mechanism rather than a sentence in a table.

## Context

This story closes four deferrals: `audit_record` five-year enforcement (OQ-P2-01, from `P2.07` AC-4), published `domain_event` cleanup at 30 days (`P7.01` AC-4), the idempotency retention horizon (`P7.05` AC-4) and knowledge retention on offboarding (`P9.09`). `database-schema.md` §5 is the authoritative table and FF-31 is the check.

## Acceptance criteria

- **AC-1** Every dataset in `database-schema.md` §5 has an enforced expiry: `audit_record` 5 years, `performance_snapshot.raw_payload` 13 months, `webhook_event.payload` 90 days, published `domain_event` rows 30 days, revoked-tenant `knowledge_chunk` deleted on offboarding, media assets by S3 lifecycle per `aws-topology.md` §5.
- **AC-2** `idempotency_key` is expired against its `expires_at` column from `database-schema.md` §3.7, closing the `P7.05` AC-4 horizon.
- **AC-3** `audit_record` expiry is executed by the privileged maintenance role, never by `vyra_app`, because FF-11 asserts the application role holds neither UPDATE nor DELETE and that assertion must still pass afterwards (ASM-P16-02). This resolves OQ-P2-01.
- **AC-4** FF-31 compares the `database-schema.md` §5 table against configured S3 lifecycle rules and scheduled purge jobs and fails when a dataset has no mechanism.
- **AC-5** Retention horizons are configuration per environment, consistent with `aws-topology.md` §4 stating backup retention is per environment.

## BDD examples

- EX-P16-03 GIVEN any dataset listed in `database-schema.md` §5, WHEN FF-31 runs, THEN it finds a scheduled purge job or an S3 lifecycle rule for it.
- EX-P16-08 GIVEN an `audit_record` beyond its five-year horizon, WHEN the retention job runs, THEN the row is expired by the maintenance role and `vyra_app` still holds neither UPDATE nor DELETE.
