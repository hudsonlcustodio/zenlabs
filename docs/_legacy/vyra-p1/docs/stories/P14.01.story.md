# Story P14.01 — performance_snapshot with normalized fields and raw payload

## User story

COMO tenant, QUERO my metrics stored both normalized and raw, PARA a platform changing what a number means does not destroy my history.

## Context

FR-PF02 requires a normalized snapshot plus the original raw payload; FR-PF03 states fields absent on a platform may be null and no parity is assumed. `performance.md` §1 makes the rule explicit: absence never means zero (I-PF1). `raw_payload` is retained so metrics can be re-normalized without refetching (I-PF2).

## Acceptance criteria

- **AC-1** `performance_snapshot` carries `publication_id`, `platform`, `external_content_id`, `captured_at`, `captured_bucket`, the nine normalized columns and `raw_payload jsonb` (`database-schema.md` §3.6).
- **AC-2** Every normalized column — `views`, `reach`, `likes`, `comments`, `shares`, `saves`, `watch_time`, `avg_watch_time`, `engagement` — is nullable, and no default coerces absence to zero (I-PF1).
- **AC-3** The table is client-owned: it carries `tenant_id` with `FORCE ROW LEVEL SECURITY` and an isolation policy, so FF-01 passes without an allowlist entry.
- **AC-4** `raw_payload` is always stored alongside the normalized fields, never instead of them and never discarded (I-PF2).
- **AC-5** The 13-month `raw_payload` retention window from `database-schema.md` §5 is declared; the job enforcing it is P16.

## BDD examples

- EX-P14-02 GIVEN a platform that does not return `saves`, WHEN the snapshot is stored, THEN `saves` is `NULL` and is never surfaced as zero.
