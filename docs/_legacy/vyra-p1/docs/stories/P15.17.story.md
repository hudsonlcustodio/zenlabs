## User story

COMO administrator, QUERO to manage plans, entitlements and subscription state and to read consumption and contribution per tenant, PARA commercial decisions rest on the ledgers rather than on a spreadsheet.

## Context

This is the Control screen referenced by `epic-P6`, the plan management UI deferred by `P6.05` and the contribution reporting deferred by `P10.07`. FR-C03, FR-C04 and FR-C05 fix the three views. FR-PC01 keeps client consumption and VYRA cost as separate ledgers, and FR-PC03 makes contribution computable from them.

## Acceptance criteria

- **AC-1** Plan and subscription management use `GET /control/plans`, `POST /control/subscriptions` and `PATCH /control/subscriptions/{id}/payment` from `api-contracts.md` §5; payment status is recorded manually per FR-BL03, with no gateway anywhere on the screen (FR-BL05).
- **AC-2** Entitlement is presented as derived from the plan and is not editable on this screen, preserving the module 16 invariant in `architecture.md` §4.
- **AC-3** Usage adjustments go through `POST /control/usage/adjustments`, which `api-contracts.md` §5 declares the only write path into the ledger outside the workflow engine, and the screen enforces its mandatory reason and `Idempotency-Key`.
- **AC-4** Contribution is presented as revenue minus provider cost minus infrastructure allocation from the two separate ledgers, never by mixing a client-usage row with a VYRA-cost row (FR-PC01, FR-PC03).
- **AC-5** Cost entries whose `source` is `estimated` are labelled as estimated, because GATE-COST01 means some providers expose no per-job cost and RISK-14 forbids inventing one.
