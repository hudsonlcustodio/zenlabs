# Story P7.05 — Idempotency table and key strategy

- **Story ID**: `P7.05`

## User story

COMO architect, QUERO one mechanism enforcing every idempotency key in the architecture, PARA NFR-15 is a property of the platform rather than a habit per feature.

## Context

ADR-0030 fixes the strategy; `architecture.md` §7 enumerates the keys. `testing-strategy.md` class 10 requires every one of them to be double-invoked with a single effect asserted.

## Acceptance criteria

- **AC-1** The idempotency table enforces uniqueness on the key, so a duplicate is rejected by the database rather than by a prior read.
- **AC-2** Every key listed in `architecture.md` §7 is representable without a bespoke table per feature.
- **AC-3** A repeated operation returns the original outcome rather than an error the caller must interpret.
- **AC-4** Records carry a retention horizon so the table does not grow without bound (P16.04).

## BDD examples

- EX-P7-05a GIVEN an operation invoked twice with the same key, WHEN both run, THEN one effect occurs and both callers observe the same outcome.
